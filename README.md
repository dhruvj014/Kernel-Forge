# KernelForge

Hand-written CUDA kernels for LLM inference, built from scratch and profiled on an RTX 4060 Laptop GPU (Ada, sm_89):

- **Fused attention.** A FlashAttention-style forward kernel, taken step by step from a naive 3-kernel baseline to an inline-PTX `mma.sync` kernel that matches PyTorch's cuDNN fused attention.
- **INT4 weight-only GEMM.** Fused dequantize-GEMV and Tensor Core GEMM kernels that make batch-1 decode of real models about 2x faster than FP16.

Both are PyTorch custom ops (`torch.library`), plug into Hugging Face TinyLlama 1.1B and Qwen2.5 1.5B, are validated against FP32 references and compute-sanitizer, and are explained with Nsight Compute evidence for every optimization step.

## Rules this project followed

- Kernels are hand-written. cuBLAS, cuDNN and PyTorch SDPA appear only as baselines in benchmark code.
- No hand-typed metrics. Every number in this README and in BENCHMARKS.md is generated from `results/*.json` by `scripts/make_report.py`.
- Hardware ceilings (DRAM bandwidth, Tensor Core and FP32 throughput) are measured on this machine, not taken from a spec sheet.
- Correctness first: FP32 references for every kernel, edge-case grids, and compute-sanitizer memcheck, racecheck, synccheck and initcheck.

## Quickstart

Needs an NVIDIA GPU with sm_80 or newer (developed on sm_89), CUDA 13, and on Windows the MSVC Build Tools. Full setup, including the Windows pitfalls hit along the way, is in [docs/env.md](docs/env.md).

```powershell
& "$env:LOCALAPPDATA\Programs\Python\Python312\python.exe" -m venv .venv   # python.org Python, not Anaconda
.\make.ps1 setup     # pinned deps into .venv, editable install
.\make.ps1 build     # torch extension + standalone CUDA binaries
.\make.ps1 test      # correctness suite (needs the GPU)
.\make.ps1 report    # regenerate BENCHMARKS.md and the results block above
```

On Linux the `Makefile` has the same targets. A fresh build takes about 10 minutes (around 100 kernel instantiations).

```python
import torch
from kernelforge import ops, quantize

q = torch.randn(1, 32, 2048, 64, device="cuda", dtype=torch.float16)
k = torch.randn(1, 4, 2048, 64, device="cuda", dtype=torch.float16)  # grouped-query: 4 KV heads
v = torch.randn_like(k)
o = ops.flash_attn(q, k, v, causal=True)

w = torch.randn(5632, 2048, device="cuda") * 0.02
qw = quantize.quantize_weight(w, group_size=128)        # packed int32 + fp16 scales
x = torch.randn(1, 2048, device="cuda", dtype=torch.float16)
y = ops.int4_linear(x, qw.packed, qw.scales, qw.group_size)
```

Put the kernels into a Hugging Face model with `kernelforge.modules.enable_kf_attention(model)` and `kernelforge.modules.quantize_linears_(model)`. `bench/ppl_eval.py` and `bench/e2e_model.py` show the full flow.

## Reproducing the numbers

```powershell
.\.venv\Scripts\python.exe scripts\download_assets.py   # TinyLlama, Qwen2.5 1.5B, WikiText-2 into .cache\hf (about 5 GB)
.\make.ps1 bench                                        # hardware ceilings + attention benchmarks
.\.venv\Scripts\python.exe bench\bench_gemm.py           # INT4 vs cuBLAS on every layer shape
.\.venv\Scripts\python.exe bench\ppl_eval.py             # WikiText-2 perplexity
.\.venv\Scripts\python.exe bench\e2e_model.py            # batch-1 decode
.\scripts\run_sanitizer.ps1                              # compute-sanitizer, all tools
.\make.ps1 report
```

Benchmarks assume the laptop is plugged in and in its performance power mode. The vendor's quiet mode capped this GPU at 30 W and halved compute throughput (see the power-limit table in BENCHMARKS.md).

## Limitations

- Inference only. No backward pass, dropout or training support.
- Attention supports fp16 and bf16 with head dim 64 or 128, and no padding masks (models fall back to SDPA for padded batches, counted in the benchmark output).
- Decode with a static KV cache under CUDA graphs uses PyTorch SDPA, because a static cache needs a mask over unfilled slots and the fused kernel has no mask input.
- INT4 is round-to-nearest with no zero points, AWQ scaling or GPTQ rounding. WikiText-2 perplexity rises about 10% on TinyLlama and 17% on Qwen2.5, which those methods would reduce.
- INT4 kernels take fp16 activations only. Both models ran in fp16 without overflow.
- The INT4 GEMM wins by 1.3x to 2.3x at batch 16 to 32, well short of the 3.4x GEMV result. Register-level dequantization with an offline weight reorder (the Marlin approach) is the known next step.
- In PyTorch eager mode on Windows, Python and launch overhead leaves the GPU idle about 80% of each decode step, so eager tokens/sec does not reflect the kernels. CUDA-graph numbers are the meaningful ones.
- No FlashAttention-2 baseline, because no Windows wheel exists and a source build was out of scope. cuDNN's fused attention is the reference instead.
- Developed and measured on one GPU (sm_89). Other architectures are untested.
- No paged KV cache, multi-GPU or batching scheduler.

## Layout

```
csrc/         CUDA kernels (attention/, gemm/, common/), torch bindings, standalone sanitizer binaries (micro/)
kernelforge/  Python package: ops (stable API), quantize, modules (HF drop-ins), bench_utils
bench/        hardware ceilings, kernel benchmarks and sweeps, perplexity, end-to-end decode
tests/        correctness against FP32 references
scripts/      report generation, Nsight Compute and compute-sanitizer runners, roofline plot
results/      benchmark and profiler JSON (the source of every published number), plots
docs/         environment, per-phase design notes, lessons learned, references
```

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs ruff, clang-format and an `nvcc` build of every kernel in a CUDA container. GitHub runners have no GPU, so tests and benchmarks run locally.
